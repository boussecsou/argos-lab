# Task 01 - Dependency Pinning

## Editorial Brief

Purpose: Explain to senior software engineers why reproducible experiments require pinned dependency versions.

Reader: Senior engineers who already understand package managers, CI, and source control, but may treat lockfiles and branch references as operational details rather than experimental controls.

Angle: Reproducibility is narrower than reliability: it protects comparability by fixing inputs, while reliability protects successful operation under expected change.

Promise: The article will distinguish reproducibility from reliability, explain why mutable branch references are risky, include a five-item checklist, and acknowledge the cost of strict pinning.

Length and voice: 500-700 words, clear and pragmatic.

## Article

# Pin the Experiment, Not Just the Code

Reproducible experiments need pinned dependency versions for the same reason they need fixed datasets, recorded parameters, and stable code revisions: an experiment is only comparable when its inputs are controlled. A reliable system can tolerate ordinary change and still behave acceptably. A reproducible experiment has a narrower job. It must let another engineer rerun the same procedure and know that a changed result came from the tested variable, not from yesterday's transitive dependency update.

That distinction matters in software experiments because most dependency specifications are deliberately flexible. Version ranges, default package tags, branch names, and installer behavior all help day-to-day development move forward. They are poor controls for experiments. npm's lockfile documentation is explicit about the role of `package-lock.json`: it records the exact generated dependency tree so later installs can generate the same tree, independent of intermediate dependency updates. npm also expects that lockfile to be committed so teammates, deployments, and CI install the same tree.

Mutable branch references are the easiest trap to miss. pip supports Git dependencies that name a branch, a tag, or a commit hash. That flexibility is useful, but the reference types are not equivalent as experimental evidence. The Git book describes a branch as a movable pointer to a commit. If an experiment depends on `main`, `master`, or a feature branch, the dependency can point to different code next week without any edit to the experiment configuration. A commit hash, especially a full hash, identifies a specific object far more directly. Tags are often treated as stable release markers, but teams should still understand their host and policy controls before treating them as immutable.

Lockfiles and pinned references do not make software reliable by themselves. They do not prove a dependency is secure, correct, maintained, or appropriate. They only make the dependency set observable and repeatable. That is still a large gain: once the inputs are stable, failures and performance changes become easier to attribute. Without stable inputs, every result has an extra question attached: did the experiment change, or did the world underneath it change?

A practical checklist for experiments is short:

1. Commit the package manager lockfile and use the package manager's frozen install mode in CI, such as `npm ci` when using npm.
2. Pin direct dependencies to exact versions for experiment branches unless a range is itself part of the test.
3. Replace Git branch dependencies with immutable commit hashes for experimental runs.
4. Record the runtime and package-manager versions, because installers and dependency resolvers can change behavior.
5. Treat dependency updates as new experimental inputs: review the diff, rerun the baseline, and label the run accordingly.

The cost is real. Strict pinning slows security updates, increases dependency maintenance, and can hide whether the system works against current upstream versions. Long-lived products still need regular update work and compatibility testing. For experiments, though, strict pinning is not conservatism for its own sake. It is instrumentation. You are preserving the evidence trail that lets a result mean what it claims to mean.
